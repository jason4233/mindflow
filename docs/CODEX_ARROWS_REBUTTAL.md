## 2. 主動自首：殘餘風險與妥協

### 2.1 演示模式的 `↑/↓` 仍會觸發節點空間導覽

- **嚴重度：中**
- **現況：**演示模式以 capture listener 攔截 `←/→` 作為上一步／下一步，但沒有攔截 `↑/↓`。這兩鍵會繼續冒泡到全域 keyboard handler，改動演示畫面背後的節點 selection；退出演示後，選取可能已悄悄改變。
- **建議：**演示模式 active 時統一 consume 四個方向鍵；若產品要讓 `↑/↓` 翻頁，應明確定義，並補演示模式事件優先序測試。

### 2.2 「最近」實際上是 90° 圓錐加權 heuristic，不是幾何最近

- **嚴重度：中**
- **現況：**候選必須落在方向軸左右各 45° 內，分數是 `軸向距離 + 偏軸距離 × 2`。因此：
  - 唯一位於右半平面、但偏下超過 45° 的節點會被完全忽略；
  - 一個 Euclidean distance 較近的斜向節點，可能輸給更遠但更對齊的節點。
- **影響範圍：**內建規整佈局通常合理；懸浮節點、manual offset、混合局部 structure 或刻意拉散的圖較容易遇到。
- **建議：**以 GitMind 實品建立更多 irregular-layout fixture，再決定是否保留圓錐、改成半平面候選，或採「主軸優先、距離次之」的分層排序。這是我為了避免斜向跳躍做的明確妥協。

### 2.3 完全重疊與完全同分沒有具備視覺語意的解法

- **嚴重度：低**
- **現況：**兩節點中心完全重疊時，彼此的 axial distance 為 0，四個方向都不會選到對方。若多個候選在同方向有完全相同的中心與分數，結果取決於 `positions` 的 `Map` 插入順序；目前雖可重現，但不是使用者看得懂的規則。
- **建議：**優先從拖曳／整理層避免完全重疊；若產品允許重疊，導覽需增加明確 tie-break（例如文件順序）或同位置循環選取。

### 2.4 只比較節點中心，極端尺寸下不一定符合「視覺最近」

- **嚴重度：低**
- **現況：**演算法使用每個 node box 的中心點，不看外框最近邊。當節點特別寬／高時，肉眼最近的節點邊界可能很近，但中心較遠，最後選到另一個節點。
- **建議：**若實測出現誤跳，改用 directional edge distance 或 rectangle-to-rectangle distance；目前測試沒有涵蓋尺寸差異極大的節點。

### 2.5 佈局切換動畫的 300ms 內，判斷使用終點而非螢幕當下位置

- **嚴重度：低**
- **現況：**layout change 時 DOM 會由舊座標 transition 到新座標，但 `positions` 已立即換成終點。動畫途中按方向鍵，選擇依最終佈局計算，可能與當下肉眼位置不一致。
- **建議：**動畫期間暫停空間導覽，或把當下 DOM rect 反算成 world coordinates；並補一條 transition 中 keydown 的整合測試。

### 2.6 大綱模式沒有實作「方向鍵跨列導覽」

- **嚴重度：低（目前較像範圍界線，不是已確認 defect）**
- **現況：**焦點在大綱的 `contenteditable` 文字時，方向鍵正確保留給原生游標，這符合「編輯中不攔截」。但純大綱／並排模式沒有另外定義 `↑/↓` 跨 outline row；若焦點不在可編輯文字上，全域方向鍵仍可能依隱藏或旁邊的 map `positions` 改 selection。
- **建議：**先確認 GitMind 大綱模式的實際語意。若需要列級導覽，應由 outline controller 接管，而不是共用 map 的空間演算法。

## 3. 已核對、目前不列為保留事項

- **一般畫布縮放：**空間判斷使用 world-space `positions`，viewport 的 uniform scale／translate 不進入計分，因此 app 內極端縮放本身不會改變候選結果。
- **摺疊節點：**摺疊後代不在 `positions`，不會被誤選。
- **編輯中的方向鍵：**表單／`contenteditable` 焦點會被 form guard 放行，不會觸發 map 導覽。

結論：我同意此次 review 的通過判定，但**不是「無保留事項」**；其中最應優先補的是演示模式 `↑/↓` 洩漏，以及 irregular layout 下 90° 圓錐 heuristic 是否真的對齊 GitMind。
