# M1 交付說明：手機可日用、資料不因更新或關閉而遺失

> 對應 `docs/android-sync-plan.md`（jason4233/mindflow#2）第 4 章的 M1。
> 本里程碑**不動同步架構**（仍走 GitHub 私有 repo），只補安全網、升級平台，並修掉 1.3 節列出的高風險 bug。
> Firebase 即時同步從 M2a 才開始。

## 1. 這一版做了什麼

| 項目 | 做法 | 主要檔案 |
|---|---|---|
| 版本閘門 | 雲端 manifest 或任一文件的 `schemaVersion` 大於 1 時停止同步並提示更新：本機不動、不重試。**M2a 寫出 v2 之前，兩台裝置都必須先更新到這一版。** | `js/sync-plan.mjs` |
| 同步競爭 | 「讀快照→套用」期間如果使用者又存檔，套用前先逐 key 比對（CAS），不一致就重來；推送前再讀一次本機；最多重試 3 次。內容完全相同的衝突不產生副本；這一輪自己剛推上去的版本不會被當成衝突。電腦與手機都已修正。 | `desktop/sync-engine.mjs`、`js/sync-mobile.mjs` |
| 本機儲存區整個遺失 | 沒有索引、也沒有任何文件時當成首次同步，只把雲端拉回來，**不會**把每份文件都記成刪除推上雲端。使用者刻意刪光時（空索引仍在）照常處理。 | `js/sync-plan.mjs` |
| 「以我為準覆蓋」 | 覆蓋前先把儲存區裡對方的版本另存成「衝突副本・覆蓋前保留」；另存失敗就取消覆蓋。 | `js/store.js`、`js/editor/main.js` |
| GAMMA 版面（R7） | 本機的版面記錄只在文件版面沒被別台改過時才套用；別台同步來的版面優先。 | `js/editor/gamma-state.js` |
| 手機同步穩定度 | 所有 GitHub 請求都加 `cache: 'no-store'`；失敗後 30 秒起跳、每次加倍、最多 5 分鐘重試；網路恢復立刻同步；在前景時每 5 分鐘先比 ETag（沒變只會收到 304）；進背景時立刻推送；記憶體內保留最近 30 筆診斷紀錄（權杖一律遮蔽）。 | `js/sync-mobile.mjs` |
| 返回鍵／進背景 | 依序處理：關掉最上層對話框 → 結束文字編輯（commit，不是取消） → 存檔並推送後回首頁。在首頁 2 秒內按兩下才縮到背景。App 暫停時先存檔再推送。 | `js/mobile-app.mjs` |
| 手機檔案備份 | 每 2 分鐘把心智圖寫進 App 私有目錄，輪替保留 10 份，內容沒變就不寫。儲存區整個不見時自動還原，完成前不讓同步開始。設定裡可以匯出（分享選單），也可以從自動備份或檔案還原；還原的文件一律以「副本」加入，不覆蓋也不刪除現有文件。 | `js/mobile-backup.mjs`、`js/mobile-settings.mjs` |
| PAT 安全儲存 | 手機的 PAT 改存 Android Keystore 加密的 `MindflowSecureStorage`。舊版留在 Preferences 的明文會自動搬過去並刪除（明文會被 Google 備份，所以要刪）。安全儲存失敗時才退回 Preferences，不會讓 PAT 消失。 | `js/sync-mobile.mjs`、`MindflowSecureStoragePlugin.java` |
| App 內檢查新版 | 讀 `releases/tags/latest`，找版號最大的 `MindFlow-<versionCode>.apk`；比手機上的版本新就在首頁提示。每 6 小時最多查一次，按「稍後」可隱藏同一版 3 天。 | `js/mobile-update.mjs` |
| QR 配對 | 電腦的「同步設定」→「在手機上配對」：在獨立視窗顯示含 PAT 的 QR。這個視窗沒有 preload、停用 JavaScript 與 DevTools、防截圖，2 分鐘後自動關閉；PAT 從不進主視窗。手機的「掃描電腦上的配對 QR」使用 ML Kit 的 Google Code Scanner，不需要相機權限；也可以把配對碼直接貼進 PAT 欄。 | `js/pairing.mjs`、`desktop/pairing-window.mjs`、`js/qr-encode.mjs` |
| Android 平台 | Capacitor 6 → 8.5.3，minSdk 24、targetSdk 36、JDK 21，edge-to-edge 由原生處理（網頁不用改）。版號由 CI 自動遞增；設好 Secrets 後固定用正式金鑰簽章。PR 也會建置並附上 APK。 | `mobile/**`、`.github/workflows/android.yml`、`docs/android-release-signing.md` |
| 測試 CI | 新增 `tests.yml`：根目錄單元測試、手機、電腦版（Windows）、觸控 E2E。 | `.github/workflows/tests.yml` |

## 2. 需要你（擁有者）做的事

1. **建立正式簽章金鑰並加入 4 個 GitHub Secrets**：照 `docs/android-release-signing.md` 操作，大約 15 分鐘。
   - 加好之前，CI 產生的 APK 仍是「拋棄式簽章」，無法覆蓋安裝前一版。
2. **唯一一次需要解除安裝的更新（R4）**：換成正式金鑰、升級到 Capacitor 8 之後的第一個 APK 必須先解除安裝舊版。步驟：
   1. 手機上先按「立即同步」，或在「手機備份」按「匯出備份」，存到雲端硬碟或傳給自己。
   2. 在電腦上確認心智圖都在。
   3. 解除安裝舊版 App。
   4. 安裝新版 APK。
   5. 電腦「同步設定」→「在手機上配對」，用手機掃描。
   6. 等第一次同步把資料拉回來。若沒有同步，就用「從檔案還原」匯入剛才的備份。
3. **之後每個里程碑打一個 `v*` tag**，讓 release 留下 `MindFlow-<versionCode>.apk`，需要時可以裝回舊版。
4. 照第 4 節的驗收清單在實機上試用約 30 分鐘。

## 6. 已知限制與風險

1. **沒有在實機或模擬器上執行過**（這個雲端環境沒有 KVM）：Keystore、edge-to-edge、返回鍵與掃描都只有編譯和單元測試。請以第 4 節的清單實機驗收。
2. 只有 debug 版 APK 的 Capacitor 會把外掛呼叫參數（含 PAT）寫進 logcat；CI 發佈的是 release 版，不受影響。
3. ML Kit 會帶入 Google 的使用統計函式庫（datatransport），因此多了 `ACCESS_NETWORK_STATE` 權限。
4. 殘留的邊角情況：一次同步在推送成功後、連續 3 次都因為本機又被修改而放棄套用時，下一次同步可能把自己較舊的版本另存成一份衝突副本（不會遺失資料，只是多一份副本）。M2b 的節點級合併會解決。
5. 本機資料遺失或從備份還原後的第一次同步是「首次同步」：只做聯集。代價是：在別台刪掉、但這台還留著的文件會被加回來；兩邊內容不同的文件會多一份衝突副本。不會刪掉或回退任何一邊的資料。
6. 手機自動備份存在 App 私有目錄（`DATA`），解除安裝 App 時會一起刪除；要跨越解除安裝，請用「匯出備份」。
7. 手機的定期備份只在 App 開著時執行；App 進背景時會再補備份一次。
8. Android 的 Google 雲端備份與換機轉移不包含 App 設定（Preferences）：還原到新手機後要重新配對一次（掃 QR 即可），心智圖本身（WebView 資料）照常還原。
9. 同步把內容寫進本機、推上雲端或讓 base 前進後，localStorage 落盤前（約 5 秒內）程式被殺時，下一次同步是首次同步（只做聯集，見第 5 點）。手機「進背景立刻推送」後被系統收掉就是這種情況：不會刪掉或回退任何資料，但在別台刪掉、這台還留著的文件可能被加回來。這是用識別碼輪換防止資料遺失的代價；M2b 的節點級合併可以縮小影響。
10. 升級到這一版後的第一次同步：若升級前在這台刪掉了文件、還沒同步出去，刪掉的文件會被加回來一次（M1-A15）。本機不留刪除紀錄，分不出「使用者刪的」與「資料遺失」，寧可加回來也不把雲端文件記成刪除。
11. 永久刪除寫到一半（文件內容已刪、索引還沒改）時程式被殺，下一次同步會把那份文件從雲端救回來一次（M1-A17）；再刪一次即可。
12. 自動還原失敗時，若「記下待保護來源」的那個小檔案（`restore-pending.json`）也因磁碟全滿寫不進去，暫停輪替就只靠記憶體，空間恢復前失去這份記憶，之後的輪替仍可能擠掉來源。要「還原失敗＋另存失敗＋記錄失敗」三件事同時發生。
    - 電腦版的記憶體狀態在 main process，重開 MindFlow 才會失去。
    - 手機版的記憶體狀態是頁面裡的備份模組變數：首頁和編輯器是不同的頁面，切換時會重新載入，所以不用重開 App，正常的頁面切換就可能失去暫停狀態。
13. **（整類已根治，見 7.7）** 「本機資料遺失、但本機儲存區識別碼還在」時，同步會信任舊 base，把本機少掉的文件當成本機刪除推上雲端，其他裝置跟著刪。原本會發生在：還原回滾後識別碼被恢復；沒有備份可還原；使用者在第一次同步前先建了新文件；索引不見但還剩部分文件。現在兩道防線：
    - 上游（M1-A21）：本機一讀不到文件索引（不存在或損壞），就在偵測的當下、使用者能建文件之前換掉識別碼。
      - 手機在頁面載入與開機還原檢查時做；電腦在頁面載入、以及 main 判定本機是不是空的那兩個入口做。
      - 下一次同步一定是首次同步（只做聯集），雲端文件不會被刪；開著同步時，本機少掉、但已在雲端的文件會從雲端拉回。
    - 還原路徑（M1-A20）：新識別碼寫成功之後，任何還原失敗都保留它。

    剩下的影響：
    - 還原撤回不完整時，首頁可能先只出現部分文件，提示文字會說明（錯誤上標 `rollbackIncomplete`）。
    - 還沒上雲（或沒開同步）又沒還原到的文件只在保留檔裡，要手動找回：手機在「從自動備份還原」選保留檔；電腦目前沒有從備份檔還原的介面，檔案留在 `backups` 資料夾。本機殘留了文件時，下次開啟不會再自動還原。
    - 首次同步的代價同第 5 點。
14. 手機保留檔最多 10 個位置（`backups/restore-failed.json`、`restore-failed-2.json` … `-10.json`），一律不覆蓋不同的內容。10 個都存了不同內容後若又有一次還原失敗，該次的來源保護不了，備份輪替會一直暫停，直到使用者手動清掉舊的保留檔。讀不到某個保留位置的狀態時，也會暫停輪替，不冒險覆蓋。

## 7. 獨立對抗式審查與處理

交出前由獨立審查代理檢查了整個 M1 的變更，並以重現測試驗證。所有發現都已處理，每一項都補了「修正前失敗、修正後通過」的測試：

| 嚴重度 | 發現 | 處理 |
|---|---|---|
| BLOCKER | 手機自動從備份還原（最多舊 2 分鐘）後，Preferences 裡較新的同步 base 會讓之後建立的文件在雲端被刪、較新的修改被舊版蓋回（電腦版的備份還原與舊資料搬入也一樣） | 新增「本機儲存區識別碼」`mindflow.sync.storeEpoch`：每次同步成功時同時存在同步狀態與 localStorage，而且**不進備份**。兩邊對不上就不信任 base，改當首次同步（只做聯集）。電腦與手機共用 `trustedBase()` |
| BLOCKER | 資料遺失後、第一次同步前若先新建了文件，「儲存區整個遺失」的防護就失效，會把雲端其他文件全部刪掉 | 同上：判斷依據改成識別碼，不再依賴「本機完全是空的」 |
| HIGH | 存檔被衝突橫幅擋住或儲存空間已滿時，按返回鍵仍會離開編輯器，記憶體裡的修改遺失 | 存檔後檢查 `canLeave`（沒被擋、沒有未存修改）才離開，否則提示 |

不變式：自動還原（或舊資料搬入）失敗後，只要新識別碼寫成功過，本機識別碼就是這次寫的新值，不會是同步狀態裡的那個。所以失敗之後不管本機長什麼樣子，都不會用舊 base 判定刪除。理由：
- 識別碼最先寫，所以有任何內容寫進去之前，新識別碼一定已經在了；
- 識別碼不列入回滾，所以不管其他 key 撤回成不成功，新識別碼都留著；
- 寫新識別碼本身就失敗時，什麼內容都還沒寫、識別碼的值也沒變過，本機和還原前完全相同，維持原值：
  - 自動還原的前提就是本機讀不到索引、也沒有任何 `mindflow.doc.*` key；
  - 所以這一刻同步會重建出零份文件、零份隔離，判定成資料遺失（`storageLost`），只做聯集。
  - 之後若在同步前先建了新文件，舊 base 會被信任；這和「沒有備份可還原」是同一種情形，由 08 的上游守門處理。

07 不增加任何寫入：留下的是已經寫成功的值，不會因為空間不足而多出新的失敗路徑。

08 的不變式：本機讀不到文件索引時，在使用者能建文件、同步能讀本機之前，識別碼已經不是同步狀態裡的那個（換成新的，或至少移除）。所以「本機遺失＋識別碼殘留」不會被同步看到，base 一律不被信任。理由：
- 同步過的儲存區一定有索引（每一輪同步都寫索引，App 存檔也寫），讀不到索引就是遺失；刻意清空的庫有空索引，不受影響。
- 手機：`js/settings.js` 在最上層呼叫，首頁 `js/dashboard.js` 與編輯器 `js/editor/main.js` 都先匯入它，所以在綁定 UI 之前執行；同步要等開機還原檢查（`startGate`），而 `restoreLatestIfEmpty` 第一行也再做一次，在任何 await 之前。

- 先 `removeItem`（不受空間限制），再盡量寫新值：兩種結果都讓 `trustedBase()` 回傳 null。識別碼不符走一般分支；沒有標記但同步狀態有識別碼也不符；升級前的同步狀態遇到新值不走升級前的分支。只剩「升級前的同步狀態＋新值寫不進去＋base 的文件 key 都在」會走升級前的分支，見下方殘留風險。
- 之後還原成功會寫新識別碼，同步成功會輪換識別碼並存進同步狀態，正常運作不受影響。
